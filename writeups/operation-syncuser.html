// 00tl;dr

A single unauthenticated SSRF/LFI utility on a Linux host was the entire opening — reading /etc/passwd through it surfaced a login password someone had hidden in a user's GECOS field. From there: a one-line sudo -l misconfig (GTFOBins' favorite, vi) gave root in seconds. Root exposed a running container's credentials and, more usefully, a publicly-served "dummy" CSS asset that was never meant to ship with real-looking secrets in its comments. A system log then handed over a second internal host, reachable only once pivoted — which turned out to be running a fully exposed web file manager leaking a plaintext credential for an Active-Directory sync account.

That sync account's name and stated purpose ("password synchronization between on-prem AD and cloud services") strongly resembled an Azure AD Connect-style service identity — and sure enough, it had been granted Replicating Directory Changes All. One secretsdump call later: every NTLM hash in the domain, including a Domain Admin. Pass-the-hash onto the DC, and a target file someone thought they'd hidden by simply renaming its extension turned up anyway — Windows "Recent" shortcuts don't forget a file's original name.

// 01SSRF/LFI foothold initial access

A full port scan of the only live host in scope turned up SSH plus two unrelated web apps. One of them — a minimal Flask service — had exactly one endpoint, and it told you how to break it in its own 404 page:

Access denied. Only the /fetch route with 'url' parameter is allowed.
Example: /fetch?url=file:///<location>, To access host files go with 'hostfs' path

The app runs in a container with the real host filesystem bind-mounted at /hostfs. Any file on the host is one request away:

$ curl 'http://<target>:23100/fetch?url=file:///hostfs/etc/passwd'
app-admin:x:1000:1000:<redacted-password>:/home/app-admin:/bin/bash
confirmed
GECOS field repurposed as a password store → direct SSH login as app-admin

[!] root cause — an SSRF/debug proxy with no auth and a host bind-mount is a full host-file-read primitive, full stop. The intended use (letting a monitoring container peek at host metrics) doesn't need unrestricted file:// + arbitrary http(s):// fetch.

// 02GTFOBins root privesc

sudo -l as the newly-landed user listed exactly one allowed command:

User app-admin may run the following commands on app-server:
    (ALL) /usr/bin/vi

vi is GTFOBins 101 — shelling out from inside it runs as the sudo target:

$ sudo /usr/bin/vi -c ':!/bin/bash'

For scripted, non-interactive root execution (handy for automating the rest of this), a one-shot variant works just as well without ever dropping into an interactive shell:

$ sudo /usr/bin/vi -c ':!<command>' -c ':q!' /dev/null
confirmed
root, two commands after landing the foothold

// 06DCSync domain compromise

That exact credential had already surfaced once — hardcoded in a leftover LDAP test script on the first box, used for a quick bind check. The account's name and purpose (password sync between on-prem AD and a cloud identity service) is the textbook shape of an Azure AD Connect sync account — which, in real deployments, is routinely granted Replicating Directory Changes All so it can sync password hashes outward. Worth testing directly, no prior DC foothold required:

$ impacket-secretsdump '<domain>/sync_user:<redacted>'@<dc-ip> -just-dc-ntlm
Administrator:500:...:<redacted-ntlm>:::
Guest:501:...:
krbtgt:502:...:
backupadmin:5101:...:<redacted-ntlm>:::   ← a second Domain Admin account
<DC>$:1000:...:
game over
full NTDS hash dump, zero interactive access to the DC — a "sync-only" account was the entire domain's blast radius

[!] why this matters most — every earlier step in this chain was a normal web/Linux foothold-and-privesc sequence. This one step is categorically different: a low-privilege identity that was never supposed to be interactively usable turned out to be Domain Admin, the moment its password leaked anywhere.

┌──(operator@kali)-[~/writeup] └─$ cat takeaways.md

key takeaways

  • Debug/SSRF utilities with a host filesystem bind-mount are full host compromises. If a container genuinely needs host file access, scope and authenticate it — never leave it as an open url= parameter.
  • GECOS fields are not a secret store. If it's in /etc/passwd, assume it's already public.
  • Audit sudo -l output religiously. One GTFOBins-listed binary in the allow-list is root, full stop.
  • "Dummy"/"example"/"test" files leak real secrets far more often than teams expect. Treat them like production config, or don't ship them.
  • Service accounts with replication rights are Domain Admin equivalent. Any identity holding Replicating Directory Changes [All] should be audited and alerted on — sync tooling needs that right on the DC side, not a reusable, phishable password.
  • Renaming a sensitive file doesn't hide it from an attacker with filesystem access. Shortcut and recent-file artifacts routinely betray a file's original name and path.
